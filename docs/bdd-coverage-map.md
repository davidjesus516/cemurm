# BDD Coverage Map — how much of the acceptance contract is verified, and what closing the gap costs

This document maps every Gherkin scenario in `features/*.feature` against the tests that
actually exist, splits the unverified remainder into the two kinds of gap that demand
different investments, and ends with a plain recommendation. It is an audit, not a
reassurance: absence is reported as absence, and every claim of coverage carries a citation
anyone can open.

## 1. Method and limits

Read this section before the numbers. It defines what the numbers are allowed to mean.

- **Nothing links a test to a scenario.** No `.feature` file is read by any test. There is no
  `cucumber`, `gherkin`, or `playwright` dependency in `package.json`, no step definitions
  anywhere in the tree, no `test` block in `vite.config.js` (so Vitest runs in its default
  `node` environment — no DOM), and CI (`.github/workflows/ci.yml`) runs exactly
  `pnpm lint → bash scripts/check-visual-contract.sh → pnpm test → pnpm build`. A scenario
  therefore never executes, and no test can "cover" a scenario by reference.
- **The matching is behavioural judgment, made by reading both sides.** A person (this pass:
  an LLM reading the feature files and the test files line by line) asks, per scenario,
  *does any test assert the rule this scenario exists to pin?* That question has no
  machine-checkable answer. The verdicts below are a documented judgment, not a measurement.
- **"Touched" is not "verified end to end."** A scenario counts as touched only when a test
  asserts its **distinguishing rule** — the thing the scenario exists to pin — and not merely
  a generic primitive it happens to use, and not a neighbouring scenario in the same file.
  Because no scenario runs, **zero scenarios are verified end to end**; the touched count is
  an upper bound on verified scenarios and is deliberately conservative.
- **The standard applied is the suite's own.** The existing tests already declare scope
  limits: `src/domain/setlist/exporters/onsong.test.js:5` covers the serializer but excludes
  the DOM download, and `src/integrations/spotify.test.js:5` excludes the two functions its
  feature's assertions need. This document applies that standard in both directions: a
  serializer test still counts as covering the OnSong export scenario (it pins the rule), and
  `external-autotagging` still scores `none`, because the functions its scenarios require are
  excluded by that same note.
- **Precision.** The scenario-level counts in §2 are the product of that judgment. Treat them
  as magnitudes, not percentages: the direction and order of magnitude are robust (the two gap
  classes are an order of magnitude apart), while individual scenario assignments near a
  boundary are judgment calls that could move a handful of scenarios either way. Row counts in
  §3 are exact — they are the scenario counts of the files themselves and reconcile with the
  tree.
- **Citations.** Every `partial` verdict carries `test file:line`. Every citation in this
  document was opened and checked to resolve to the line claimed. Where no citation could be
  produced, the verdict is `none`.
- **Scope.** Documentation only. No test, `.feature` file, source file, or existing document
  was modified.

### Findings the matching surfaced (not coverage)

1. **Two scenarios contradict the code that implements them.** `features/offline-edit-conflict-policy.feature:47`
   requires a recorded tie-break rule for equal timestamps; the code has none — the test itself
   records the divergence at `src/domain/setlist/collab.test.js:124` (equality replays because
   the comparison is `>`). `features/music-theory.feature:95` requires the slash bass to
   transpose with the chord (`G/B` up two → `A/C#`); `src/domain/music/transpose.test.js:128`
   pins the opposite (`G/B` + 1 → `G#/B`, bass rides along verbatim). Neither scenario is
   counted as covered — a contradiction is a finding, not coverage.
2. **A whole module's tests have no scenario at all.** `src/domain/offline/drainFailure.test.js`
   (28 test blocks) pins how a failed offline drain is classified — transient, permanent,
   quarantine, "changes were set aside". No `.feature` file specifies quarantine or retry
   semantics anywhere (`grep` over `features/` finds no such wording). This is BDD silence in
   the other direction: tests without a spec, roughly a tenth of the suite.
3. **Some of the contract has no implementation to test.** The three `education-*` features
   (46 scenarios) are assigned to no hito (`docs/mvp-scope.md:18`) and no education code was
   found in `src/**`. Hito 6 is "Implementation status: not started"
   (`docs/mvp-scope.md:245`), and no analytics / offboarding / erasure / data-export code was
   found either. Range-profile detection in `personal-preferences-and-adaptations` (six
   scenarios from line 246) has no implementation under any name. Neither option B nor option
   C can verify behaviour that does not exist.

## 4. Coverable-but-uncovered — the cheap-win list

**First, the honest headline: no feature is predominantly domain-pure.** Asked "which
features are pure domain and have zero tests", the evidence answers *none* — every one of the
45 features is majority UI, repository, offline, or RLS behaviour. The coverable gap does not
live at feature level at all; it lives in **modules**, scattered as 28 minority scenarios
inside 9 otherwise-unreachable features. That scattering is itself a finding: option B buys
piecemeal wins, not a large verified slice.

none of it covered:

Two boundary notes that argue the line is drawn by *placement*, not by capability:

- `features/setlist-creation.feature:23` (estimated duration) is pure arithmetic —
  `computeTotalSeconds` at `src/data/repositories/setlists.js:1211` — but it sits in a
  repository module, so it falls on the not-coverable side of the line by architecture, not by

  the not-coverable side.

## 6. Decision output

**The evidence supports option C as the load-bearing investment, with option B as a small
parallel item — not as an alternative to it.**

- **C (browser/E2E harness over the local Supabase stack) is the only option that can verify
  the contract.** 653 of 713 scenarios — every feature, every shipped hito — are unreachable
  from a `node`-environment test. No amount of domain-level testing changes that number by
  more than a rounding error.
- **B (Gherkin runner over `src/domain/**`) closes 28 scenarios — 4% of the contract.** That
  is not a criticism of B: it is cheap (five modules, all pure, one of them already under
  test), and its real return is *divergence detection*, not coverage — the two spec-vs-code
  contradictions found while writing this document both surfaced inside characterization tests
  of already-tested modules. Extending that style to the five untested modules in §4 is where
  the next contradictions would surface, for the cost of a few dozen assertions.
- **B alone cannot answer the question this artifact was written to answer**, and C alone
  would leave the domain rules verified only through the UI, where a wrong chord spelling is a
  screenshot diff instead of a failing assertion.

**The honest counter-argument against C (the case for B-only, or for neither):** E2E over a
seven-hundred-scenario UI contract is the most expensive and flakiest harness available, and
it would be written against an incomplete product — education, all of Hito 6, and the
range-profile logic do not exist yet, so a large share of the E2E suite would encode
un-built behaviour and rot before it ever runs green. It also needs a live database in CI
(the local Supabase stack), which this repo's workflow does not currently provision. That
argument points at a third option neither B nor C: a **component-level DOM harness**
(`jsdom` + Testing Library) for `src/features/**`, which would reach the majority of the 653
without a browser or a database — at the cost of never testing RLS, the service worker, or
the offline queue, which together are exactly the surfaces this app's offline-first promise
rests on.

**If only one thing is funded:** C, scoped first to the shipped hitos (1–4), because that is
where 100% of the implemented-but-unverified contract lives. **If two things are funded:** C
then B, and land B first only if the goal is finding spec drift cheaply rather than
verifying the product.
